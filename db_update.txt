2. LATEST DATABASE RULES / DESIGN
==================================================

2.1 Restaurant submission and approval flow
- New restaurants from users do NOT go directly into Restaurant.
- User-submitted restaurants first go into RestaurantApproval.
- API-retrieved conflicting restaurants may also go into RestaurantApproval.
- curr_restaurant_id in RestaurantApproval can be NULL if the restaurant is completely new.
- RestaurantApproval status values:
  0 = not reviewed
  1 = accepted
  2 = rejected
- RestaurantApproval source values currently considered:
  API / User
- When admin accepts an approval item:
  - a new Restaurant record is inserted
  - if this approval is replacing an existing place at the same location, the old Restaurant is disabled
- Posts linked to a newly submitted restaurant remain pending until admin approval is completed.

2.2 Restaurant and cuisine design
- Restaurant has exactly 1 main cuisine.
- Restaurant.main_cuisine_id points to the main cuisine.
- Additional cuisine tags are allowed through Restaurant_Cuisine.
- Cuisine.isPrimaryOption indicates whether a cuisine can appear in the user submission form as a primary/main cuisine choice.
- User flow:
  - user selects only 1 main cuisine when submitting a new restaurant
- Admin flow:
  - admin can assign multiple cuisines/tags to a restaurant through Restaurant_Cuisine

2.3 Post rules
- Every Post must be tied to a Restaurant.
- A free-floating post without restaurant linkage is not allowed.
- Post keeps both title and caption.
- Current important Post state flags:
  - isPending = waiting for approval / not yet publish-ready
  - isRemoved = deleted or hidden by user/moderation
  - isBlocked = blocked from being published / access restricted
- Post.saveCount means the number of times this post appears in post-type collections.
- Likes are post-only.
- Restaurant likes are not modeled separately.

2.4 New restaurant + pending post workflow
- If user creates a post for a restaurant not found in the current system:
  1. create RestaurantApproval row
  2. create Post row with isPending = true
  3. admin reviews restaurant approval and related pending post
  4. if approved, insert Restaurant and allow post to become visible

2.5 Collections design
- collections.collection_type determines what the collection stores.
- Supported collection types:
  - RESTAURANT
  - POST
- Each user is expected to have default collections, including:
  - one default restaurant collection
  - one default post collection
- collections_item now supports saving either a restaurant or a post.
- collections_item contains:
  - item_Id
  - collection_Id
  - restaurant_id
  - post_id
  - savedAt
- Rule for collections_item:
  - at least one of restaurant_id or post_id must be NOT NULL
  - both cannot be filled at the same time
- collections_shares is still used for collection sharing.

2.6 Hashtag design
- Hashtags are normalized.
- hashtag stores hashtag master records.
- post_hashtag handles many-to-many relationship between Post and hashtag.
- Hashtags are no longer planned as a JSON/object blob inside Post.

2.7 Followers
- Follower models user-to-user follow relationships.
- follower_id cannot be the same as following_id.

2.8 Swipe / BlindBox history
- swipe_history keeps record of user-restaurant swipe interaction history.
- Current simplified design only records:
  - user_id
  - restaurant_id
  - swiped_at
- Detailed swipe action type is currently not required.

2.9 Comment / reply / report moderation
- Comment and Reply remain separated.
- The old Report table is retained as the active reporting model.
- Report is used instead of Comment_Report.
- Report status values currently used:
  0 = Pending
  1 = Remove
  2 = Dismissed
- Report currently contains:
  - report_Id
  - user_Id
  - post_Id
  - comment_Id
  - reason
  - status
  - created_At
  - details

2.10 Notifications
- Notification_Settings currently stores toggles for:
  - likes
  - comments
  - followers
  - mentions
  - push
  - inApp
- Notification currently uses the minimal structure:
  - id
  - user_id
  - content
  - redirect_To
  - created_At
  - isRead
- Notification now includes read state with default FALSE.
- Richer notification structure such as type / actor_user_id is not part of the current applied schema yet.

5. PREVIOUS / OLDER DATABASE DESIGN CONTEXT THAT MAY AFFECT THE PROGRAM
==================================================

Below are the important earlier design assumptions / older schema directions that may affect existing code, services, SQL, validation logic, or UI flow.

5.1 Collections previously used post-only structure
Old direction:
- collections_post existed instead of collections_item
- saved logic was more post-focused

New direction:
- collections_post is replaced by collections_item
- collections can now store restaurant or post depending on collection_type

Affected program parts:
- save feature
- collection insert/update/delete logic
- collection retrieval queries
- default collection creation logic
- BlindBox save flow
- any API/service method assuming collection items are always posts

5.2 Hashtags were previously considered as object/blob inside Post
Old direction:
- hashtags may have been stored directly inside Post as object/json-like data

New direction:
- hashtag + post_hashtag normalized many-to-many design

Affected program parts:
- post create/update request payloads
- hashtag parsing logic
- hashtag search queries
- trending hashtag logic
- any frontend code expecting hashtags as a single raw field in Post

5.3 Cuisine design changed from simple single field to mixed primary + tag model
Old direction:
- cuisine/category was more like one direct value on Restaurant
- no mature many-to-many admin tagging flow yet

New direction:
- Restaurant.main_cuisine_id = exactly one main cuisine
- Restaurant_Cuisine = extra admin-managed tags
- Cuisine.isPrimaryOption = user submission form control

Affected program parts:
- restaurant create form
- admin restaurant edit form
- restaurant search/filter logic
- restaurant detail page
- seed data for cuisine list
- any code assuming restaurant has only one cuisine field with no tag table

5.4 New restaurant submission flow is stricter now
Old direction:
- restaurant approval existed, but the pending post + new restaurant workflow was less clearly defined

New direction:
- user-submitted restaurant goes to RestaurantApproval first
- related post stays pending until approval
- acceptance inserts new Restaurant and may disable old Restaurant

Affected program parts:
- post creation flow
- admin approval dashboard
- restaurant search before posting
- pending post visibility rules
- moderation / review workflow
- restaurant replacement logic

5.5 Restaurant replacement rule is now more explicit
Old direction:
- conflicting restaurant data was discussed, but not fully committed to insert-new-and-disable-old behavior

New direction:
- on approval, insert new Restaurant
- disable old Restaurant if replaced

Affected program parts:
- restaurant sync/import logic
- admin approval actions
- restaurant active/inactive filtering
- restaurant lookup queries
- historical post-to-restaurant references

5.6 Collections item integrity logic changed
Old direction:
- one item reference path was still being debated

New direction:
- collections_item contains collection_Id plus nullable restaurant_id / post_id
- exactly one target must be selected

Affected program parts:
- backend validation
- collection insert service
- DB constraints/check constraints
- fetch queries for collection items
- serialization / DTO mapping for collection item responses

5.7 Notification design remains minimal for now
Old direction:
- simple message-like Notification structure

Current applied direction:
- minimal Notification with content, redirect_To, created_At, isRead

Possible future direction discussed:
- type + actor_user_id, possibly entity reference fields

Affected program parts if upgraded later:
- notification creation service
- notification rendering logic in frontend
- redirect handling
- unread count queries
- any SQL that assumes Notification only has content + redirect_To

5.8 Post state handling is now more explicit
Old direction:
- pending / removed / blocked meanings were not fully clarified
- previous schema used isBlock naming

New direction:
- isPending = waiting approval
- isRemoved = deleted/hidden by moderation or user
- isBlocked = blocked from publishing / access restricted

Affected program parts:
- post listing queries
- moderation service
- user post management screen
- admin approval logic
- post visibility rules in feeds/search/profile

5.9 Report table retained instead of Comment_Report
Old direction:
- Comment_Report had been discussed as a possible dedicated report table

Current applied direction:
- old Report table is retained as the active reporting model
- status values now align to:
  0 = Pending
  1 = Remove
  2 = Dismissed
- created_At is the kept timestamp column

Affected program parts:
- report submission flow
- moderation dashboard
- admin review actions
- report query logic
- any code written for Comment_Report should be reviewed or removed

6. IMPORTANT IMPLEMENTATION NOTES
==================================================

- Any existing code using collections_post should be reviewed.
- Any existing code still using Saved as the main save source should be reviewed.
- Any existing code treating hashtags as a raw Post field should be reviewed.
- Any existing code treating cuisine as only one plain restaurant field should be reviewed.
- Any existing code publishing posts immediately for brand new restaurants should be reviewed.
- Any code still referring to Post.isBlock should be updated to Post.isBlocked.
- Any code still referring to Report.createdAt should be updated to Report.created_At.
- Any code written against Comment_Report should be reviewed because Report is the retained model.
- Image storage is intentionally not finalized in this note and should be treated separately.
- User.password still exists in the current database, but migration to Supabase Auth is expected later and is intentionally ignored for now.
